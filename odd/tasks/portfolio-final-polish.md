### CSS-to-utilities migration (user's original "injected CSS" complaint)
The prior CSS audit (`/tmp/portfolio-audit2/css-tailwind.md`) found ~2,500 lines of hand-written component CSS with zero `@apply`; a large share is static layout/box-model (`display:flex`, `gap`, `padding`, `position:absolute`, radii) that Tailwind utilities cover, split across global stylesheets and a separate responsive file, so editing one component means editing two or three files. Rule for every area: move static layout, spacing, sizing, radius, typography, and token colors into utilities (responsive/dark/hover variants) in the component markup; keep in CSS only what utilities cannot express cleanly (keyframes, masks, multi-stop/generative gradients, complex pseudo-elements, cascade-dependent reduced-motion overrides). Keep class names that scripts or tests use as hooks. Readability is an acceptance criterion, not only pixels: no arbitrary color/shadow literals in class names (`bg-[rgb(…)]`, `shadow-[0_…_rgb(…)]`) — add named tokens to `@theme inline` instead (alpha inside the token when an E2E asserts plain `rgba`); no arbitrary selector variants (`[&:not(.x)]:`) — add a named `@custom-variant`; multi-declaration pseudo-elements stay as a small scoped `<style>` rule; the JetBrains font is `font-code` (`--font-code` theme token); no hand-written vendor prefixes (Lightning CSS derives them from browser targets). Acceptance gate per area: `/tmp/vr/shoot.mjs` before/after (7 routes × desktop 1280 / mobile 390 × light/dark, reduced motion) pixel-identical within 2% fuzz, plus full Vitest, build, and the relevant Playwright specs.
